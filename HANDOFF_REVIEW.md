# Observation-order fix and next hardware review

## Verified source and deployment boundary

Before implementation, read-only deployment checks confirmed the healthy previous
playback-tested image, no process restarts, fresh room evidence and no owned lease.
Its controller file hash matched the earlier source checkpoint exactly. The
retained ownership-loss diagnostic was physical `unexpected_source_uri` during
transition. Both observation-order characterizations reproduced against that
unchanged checkpoint. Current deployment remains unchanged by this review.

## Targeted fix

The first explicit load uses the existing bounded handoff deadline. A physical
notification with the exact discovered-host/dynamic-port, ordered zone/room/device
path and numeric punch parameter may be incomplete evidence while that handoff is
pending. This neither marks ownership nor sends Play. The virtual relay URI must
match the current load exactly, and every leased renderer must have a new complete
read after loading began. Event-only observations cannot substitute for these reads.
Unknown forwarding shapes, contradictory virtual sources, new Spotify evidence,
changed topology, stale observations and deadline expiry still fail closed.

The adapter invalidates in-flight source reads at load start using its existing
device version mechanism. Late command successes/faults and requests using an old
token cannot revoke a newer lease. Released leases are never reconstructed from
observations. UPnP notifications carry no selection generation: ambiguous old
notifications cannot confirm a new load; contradictory notifications remain
conservatively revoking rather than being guessed stale. Poll ordering is unchanged.

## Silence: known boundary versus missing evidence

The latest failed handoff reached the Python backend and URI-loading step, then
failed source confirmation before Play. That explains that disconnect, not all
previous silence. Earlier hardware reported PLAYING with retained ownership,
low room/speaker volume and mute off, but no HTTP/byte trace was captured. A
reported transport state, or even delivered bytes, is not proof of audible output.

`receiverConnections[*].playbackTimeline` now keeps 64 in-memory sanitized events,
correlated by a local numeric attempt, not an account/session/track/room identifier:

1. Incoming playback-protocol event (not every such frame is a Play request).
2. Player play attempt; upstream metadata and streaming-URL lookup results.
3. Relay registration; Node play result.
4. Node `rooms[*].lastPlaybackEvidence` separately records URI-load and Play SOAP
   acknowledgement/failure/timing and source confirmation. Successful commands also
   return this evidence to the Python attempt timeline.
5. Incoming relay request, GET/HEAD/range flags, upstream HTTP status, allowlisted
   content-type category and presence of Content-Range.
6. First/total bytes successfully written to the downstream connection, completion
   or error. This is application write evidence, not decoder or acoustic evidence.
7. Observed renderer transport changes, separately from command acknowledgement.

No signed URLs, relay keys, request/response bodies, range values, exception text,
track metadata, endpoints or hardware identities are retained by this timeline.
Events recorded after awaited operations represent observation/reporting time;
SOAP durations and Node start timestamp are separate. Metadata preloads outside a
play attempt have attempt zero and must not be mistaken for the active load.
Diagnostics are memory-only, not a credential backup or persisted raw capture.

Relay HTTP transport, accepted statuses, copied headers, range forwarding and
authentication lifecycle are unchanged. Synthetic tests cover full byte delivery,
206/If-Range forwarding, HEAD, 416, upstream rejection and expired relay keys.
No hardware audio requests have been generated by this investigation.

## Volume and reconnect

The upstream [node-raumkernel examples](https://github.com/ChriD/node-raumkernel#examples)
confirm `setVolume` for a whole zone and `setRoomVolume(roomUDN, volume)` on its
virtual renderer for one room. The existing candidate matches the live declared
InstanceID/Room/DesiredVolume arguments and serialized-SOAP tests; no second setter
is attempted after a reset. Hardware still rejected that candidate with a SOAP-path
reset, while Python-to-Node returned HTTP 200. Fresh authoritative observations
retained ownership and volume readback remained unchanged. A later Stop reset
released ownership. Reset cause and audible output remain unresolved; setters and
getters alone prove neither application nor external takeover.

Volume reconciliation now explicitly requires new complete reads, not changed
event objects. It never restores a revoked lease. Further writes on an uncertain
lease remain blocked. A late volume response cannot revoke a newer selection.

Receiver diagnostics now distinguish `selection_replayed` and `selection_limit`.
A duplicate handshake does not reinstall tokens, replace the player or grant
ownership. The existing active session is preserved, but the duplicate receives
409. Safe acknowledgement was considered and deferred: current room-owned state
does not expose proof of the identical backend token, and heartbeat would extend
the lease. This change does not add a new admission API just to acknowledge retries.
Released-session retries remain rejected; no seen IDs are cleared or invented.
